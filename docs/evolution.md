# 工作流也值得时不时折腾一下

[English](evolution.en.md)

我想把自己的 Agent 工作流继续折腾好一点：隔一段时间逛逛 GitHub Trending，看看高星项目，也看看研究团队最近在试什么。有意思的工具就拿自己的任务试一轮，合适的接进来，用着别扭的再换。

下面整理的是我希望沿用的做法。你可以挑适合自己的部分抄作业，也欢迎带着你的任务和结果来拍砖。这里是流程说明，实际安装、配置修改和定时任务要另行执行。

## 从一个具体问题开始

我的建议是每月抽一点时间回顾，或者遇到反复出现的问题时就顺手研究一下。比如 PDF 提取总把双栏顺序弄反，这就值得找个新方案试试。逛 Trending 时发现了好东西，也可以先记下它能帮自己做什么，再找一个真实任务比较。

记录不用写成长报告，能让下次的自己接着做就行：

| 项目 | 要写清楚的内容 |
| --- | --- |
| 想解决什么 | 哪种输入出了问题，现在怎么做，希望变成什么样 |
| 从哪找到的 | 官方仓库或论文、阅读日期和版本；仓库记下 commit/tag |
| 接到哪里 | 准备替换哪一步，还是补上现有工具做不了的事 |
| 值不值得试 | 许可和维护情况，依赖、平台、数据去向、遥测、权限与费用 |
| 怎样比较 | 现有方案 A、新方案 B，这次改什么，怎么算通过，什么时候停 |
| 最后怎么办 | 留下、局部试用、放弃或待验证；出了问题怎么恢复 |

我也希望把已经接通的服务用起来，让检索、文档、浏览器和本地、云端执行能配合做事。模型选择同样留点弹性：简单、范围明确的活，可以交给合适的更便宜模型，或者把同一模型的推理强度调低。具体用哪个，按当时的能力和成本来选；做比较时再记清实际型号和设置。

## 拿同一个任务，认真试一轮

1. **先留好退路。** 保存原文件、版本、依赖和恢复副本，读一下许可证与安装脚本。在当前授权内，给新方案准备独立的试用环境。
2. **想清楚怎样算有用。** 准备几份用来修改方案的样例，另外留几份到最后验收，再加上原来就能处理好的样例。提前定好预算、重复次数和停止条件。
3. **检查方法也试一下。** 放入一个已知正确的结果，再放一个看着合理但有错的结果，确认检查器能分清。答案和检查器放在候选无法修改的位置。
4. **让 A/B 从同一起点出发。** 分别使用干净目录，保持输入、权限、模型、推理强度和预算一致。这一轮主要改一个因素；如果比较的就是模型或预算，就把它写清楚。成功、失败、超时、环境故障都留记录，测不到的指标也注明。
5. **打开结果看看。** 代码跑测试，文档看顺序和版面，浏览器任务看最终页面与状态。比较文风时，可以先隐藏方案名称再请独立审阅者看；模型评价和真人反馈分开记。
6. **请另一双眼睛复核。** 把目标、原始结果、判定标准和失败样例交给独立审阅者。有道理的问题自己复现、修正，再跑受影响的检查。只有自查时，就如实记成自查。

试几次，通常就能发现一些明显问题。至于能不能稳定帮上忙，要看预先安排的重复结果。中途改了方案，就给它一个新版本，成绩也分开记，方便以后回头看。

## 什么时候值得留下来

拿双栏 PDF 举个例子。**下面是演示方案，尚未执行**；这些数字可以按自己的任务调整，但要在看结果之前定好。

> A 是原提取器，B 只增加版面排序。准备 3 份开发文档、4 份留到最后验收的文档，再用 2 份单栏文档检查原有功能。人工核对阅读顺序，固定文件和检查器。每个方案从干净目录跑 2 次，失败也记下来。B 两轮都读对验收文档、没有新增单栏错误或丢字、总耗时不超过 A 的 1.5 倍，独立复核也通过，就把它接进这个提取流程。否则继续试，或者恢复 A。这个结果的适用范围是这组文档，遇到新版式还要检查。

决定留下，就记好最终文件与哈希、调用入口、适用范围和恢复命令，第一次用到真实任务时再检查结果。还没跑过验收的，先放在“待验证”；出了问题，按记录恢复原方案。证据校验器可以帮忙查记录是否齐全，实际效果仍要看产物和验收。

## Harness² 给我的启发

我之前提到过 Google 的 **Harness²（harness squared）**。它研究的是：让 Agent 提出工作方式的改动，实际跑一跑，对比结果，再把有依据的改动和经验留下。模型权重保持不变，调整的是模型周围的提示词、工具、技能和编排等。这是 Google Research 仓库里的研究项目，作者包括 Google Cloud AI Research 的研究人员，仓库也注明它不是 Google 正式支持的产品。[仓库](https://github.com/google-research/harness2) · [论文 v1，2026-10-09](https://arxiv.org/html/2610.14224v1)

我想借鉴的是它愿意尝试、也回头比较的做法。具体落到自己的工作流，还是拿自己的任务来检验。上面的留出验收、独立检查和恢复方法，是我为这套流程选的条件；论文里的实验结果留在它的实验范围里。

你如果试过更顺手的办法，欢迎分享工具、任务和结果。也许下一次值得接进来的东西，就在大家的日常用法里。
