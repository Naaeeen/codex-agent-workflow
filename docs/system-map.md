# 工作流的六层结构

这套工作流的入口是自然语言任务。完成一个任务需要模型推理，也需要把当前工程、可用工具、执行权限和结果证据带进同一个过程。这里把这个包围模型的运行环境称为 harness。

## 任务实际怎样走

1. 主代理先读任务、适用的 AGENTS.md、仓库现状和有关文件。这个阶段要得到可观察的完成条件。例如“添加导出”还不完整，“正常数据能导出，空数据有明确信息，原有筛选不变”更容易验收。
2. 根据不确定性选方法。API 语义不清就查官方文档，代码影响不清就查调用路径，需要浏览器证据就打开实际界面。相关 Skill 给出步骤、边界和输出约定。
3. 选择执行位置和接口。CLI 适合本地可重跑命令，MCP 提供服务或结构化工具接口，浏览器用于实际界面。需要本机文件或登录态时，工作通常在本机完成。云端需要可用环境、可移交输入和对应授权。
4. 独立子任务可以委派。每个子任务要有范围、文件归属、材料和完成条件。主代理随后核对返回的证据。多人共享目录时，文件归属和隔离工作树防止互相覆盖。
5. 运行能回答完成条件的检查。静态检查、单元测试、集成结果、浏览器行为和真实用户意见提供不同的信息。保存失败、基础设施错误和未执行项，修正后重跑受影响部分。
6. 交付结果和证据，把后续继续所需的决定写在项目记录中。一条规则反复出问题时，再提出候选改法，与原做法比较并独立复核。

## 各层具体负责什么

| 层 | 载体 | 具体影响 |
| --- | --- | --- |
| 会话与运行设置 | config、profile、宿主与本次启动参数 | 模型选择、推理强度、搜索、权限等。磁盘默认值可能被本次会话覆盖 |
| 常驻工作约定 | 用户与项目 AGENTS.md | 开工前看什么、怎样协作、何时才算完成、哪些动作需要授权 |
| 按任务的方法 | Skill 名称、描述、正文和参考文件 | 确定某一类任务的步骤。先根据描述发现，再按需读正文 |
| 任务执行者 | 主代理和子代理角色 | 用独立上下文处理可拆分任务。角色文件定义职责，实际能力和工具权限受宿主约束 |
| 外部能力 | CLI、MCP、浏览器、连接器 | 读取材料、执行工具、访问服务和操作界面，返回可供判断的结果 |
| 反馈与状态 | 检查结果、评审、任务账本、交接记录 | 让“已经做完”有可核对依据，并支持中断后继续 |

## 最容易混淆的三个地方

配置文件里出现一个开关，只能证明保存了这个值。还要看客户端版本、信任与宿主是否接受它，以及当前会话怎样加载。详细对照见 [设置审计](settings.md)。

写一个名为 reviewer 的角色，会给模型一个职责描述。隔离权限则由运行环境实际执行。公开包同时保留原角色文件和当前文档对应的副本，读者可以核对两者的差别。

安装工具解决可用性。Skill 解决何时使用和如何验收。一次运行通过解决当前例子的正确性。想知道这项改动是否值得长期采用，还需要原方案、候选方案、相同任务和不受候选影响的验收。

## 从哪个文件开始复制

完整工作约定在 [global-AGENTS.md](../templates/global-AGENTS.md)。按任务的方法见 [工作流说明](workflows.md) 与 [Skills 清单](skills-catalog.md)。实际配置和工具来源见 [设置说明](settings.md)。用新目录执行 bootstrap 可以先验证本项目范围的约定、Skills 与角色。完整机器配置含占位项，应按设置文档逐项接入自己的环境。
