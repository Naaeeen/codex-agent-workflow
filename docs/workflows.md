# 实际工作方法：从规则到可验收结果

我把自己的 Agent 工作方法分成几个可以接起来的动作：先弄清要交付什么，再找证据、分工、实现、复核，最后留下能接着做的记录。下面把每一步怎样做、为什么做、哪里容易出问题展开，方便你挑适合自己的部分试用。欢迎带着具体任务来提建议，尤其是这些步骤在哪种情况下反而增加了负担。

说明依据是本机现行全局工作约定与所选 Skill 正文，描述的是**已经配置的方法**。本次读取与验证另有审计记录；历史执行情况、方法效果需要对应任务证据。

## 先看三层怎样分工

| 层 | 放什么 | 什么时候读 | 为什么这样分 |
| --- | --- | --- | --- |
| 全局 AGENTS.md | 跨项目的范围、协作、验证、隐私、授权默认值 | 由支持该机制的客户端载入；实际发现路径须核对 | 每个任务都要守的边界集中维护 |
| 项目 AGENTS.md 与 README/CI | 当前项目入口、架构、命令、交付位置、项目特有验收 | 进入该项目时 | 防止把一个项目的栈、部署权限、旧 PASS 搬到另一个项目 |
| Skills 与引用材料 | 某类任务的具体方法，按描述选择，再读所需正文和引用 | 任务匹配时 | 名称/描述承担路由，细节按需读取，减少无关上下文 |

完整个人规则见 [global-AGENTS.md](../templates/global-AGENTS.md)。轻量项目入口使用[六个便携方法 Skills](skills-catalog.md#公开包里的六个可复用-skills)，完整复现使用[用户 Skill 导出](../environment/bundle/codex-home/skills/)及配套工具。按自己的任务选择需要的方法，来源、许可与隐私替换均有单独记录。

规则优先级由运行客户端的指令层次决定；本模板明确要求服从当前请求和更具体的项目规则，不能借此覆盖系统、开发者或宿主权限。文件放对位置也不等于已经加载：在新的目标会话确认发现情况。全局文件是常驻候选上下文，Skill 正文按需读取；因此全局只保留默认决策，详细操作留给 Skill。这里没有测量 token 节省，也没有宣称“越短越好”。

### 完整全局规则每节在管什么

| 原节名 | 具体决策 | 适用例子 | 容易误用 |
| --- | --- | --- | --- |
| Scope and execution | 先查状态、版本、能力与验收；授权内可逆工作继续 | 改导出功能前读现有测试命令、Git 状态 | 把“主动执行”当成可擅自发布 |
| Communication and judgment | 事实、判断、限制分开；质疑有依据的假设 | 报告只有本地验证，远端尚未验证 | 用免责声明代替结论，或迎合每条评审建议 |
| Delegation and cost | 独立问题并行、文件归属明确、重大改动新上下文复核 | API 与 UI 分属不同 worker | 多个 agent 同改一文件；更换名字冒充独立复核 |
| Implementation and verification | 用项目栈，行为变更先 red，再修复和相关验收 | 重复提交 bug 先失败回归 | 编译通过便宣称完整用户流程成功 |
| Security and external actions | 保留权限边界；外部写入按明确授权；全局改动先备份 | 可本地草拟 PR；推送需已有对应授权 | 指南推荐插件便直接安装、开权限、上传 |
| Context and evidence | 每个重要阶段留下需求到验证的证据链 | 实验失败后保留失败条件，更新下一步 | 每个小改都做仪式化实验，或只记最后一次 PASS |

## 1. 开工：先定义结果，再选工具

**何时用：** 进入新项目、接到新行为变更、恢复长任务。小修改用几行记录即可。

**动作：** 读适用规则与入口；检查相关文件、工作树、manifest、lockfile、CI；用一句话写用户结果，列出可以观察的验收。复杂任务补依赖、风险、文件归属和停止条件。先问“已有工具能做什么”，再选方法，不能把另一个客户端的 tool、hook 或角色名字当成可调用能力。

**为什么：** 让方案对准当前真实状态，保护已有工作，避免先搭一套工具再寻找用途。

**例：** “CSV 下载需保留中文并防止重复点击产生重复请求。”先定位下载处理和现有测试，确定实际 package manager；验收是保存文件的内容与浏览器请求次数，而非只检查按钮是否出现。

**容易踩坑：** 忽略未提交改动；直接运行陌生框架命令；用上次成功或现有截图替代这次验收。可复制 [任务简报](../templates/task-brief.md)。

## 2. 查资料：从会改变决定的问题出发

**何时用：** 不熟悉、可能变化的 API，重要技术/产品选择，多源研究。

**动作：** 把问题拆成可独立回答的子问题；先查本项目版本和代码，再查可用文档工具或官方材料；阅读关键正文与限制，保留链接、日期/版本、实际读到的范围。遇到冲突，检查是否版本、环境、定义不同。记录事实、推断、未验证假设，不用搜索摘要代替全文阅读。

**为什么：** 搜索量不能替代证据质量；同一 API 名称在不同版本可能有不同语义。

**例：** “该版本流式响应取消后是否停止后端任务？”官方文档给合同，源码解释实现，受控测试检查本项目行为。若只有客户端取消成功，不能声称服务器停止计费。

**容易踩坑：** 把转载数量当独立印证；要求装新 MCP 才能研究；把提供者示例当已调用的工具。模板：[来源表](../templates/source-record.md)。

## 3. 每个重要阶段走完证据循环

**何时用：** 较大的研究、计划、设计、实现、Agent 方法改动。只改一处错字不需要整套流程。

**动作：** 在阶段进入、假设改变/检查失败/评审发现问题之后、阶段验收之前，重看：需求 → 证据 → 决定 → 修订 → 验证。每个重要子项保留结果，不能用一个总 PASS 覆盖所有缺口。选定问题解决后停止这条工作线。

**为什么：** 计划与事实容易在长任务里分离；循环应响应新信息，而不是按固定轮数消耗时间。

**例：** 研究发现浏览器录音的权限限制后，先修订“自动开始录音”的产品承诺，再改实现和拒绝权限的验收，而非继续执行旧计划。

**容易踩坑：** 只有开工时读方法，后续证据改变却不改方案；或无新风险仍不断重跑绿色检查。模板：[证据记录](../templates/evidence-record.md)。

## 4. A/B、负对照和失败保留

**何时用：** 重要且确有候选的技术/界面选择；重复出现的 prompt、Skill、harness 问题。确定性 bug 优先用能区分成因的复现，不必包装成 A/B。

**动作：** 试验前固定任务、输入、基准版本、验收和淘汰条件；一次明确主要变化因素。Agent 比较尽量固定模型/effort、工具、权限、环境；每次从独立目录中的同一 fixture 开始。让 grader 先拒绝一个合理但错误的结果，也接受一个合法的替代实现；被测 agent 不能改 grader 或期望。保留失败、超时、中止、基础设施故障，交代分母。重要比较不能运行时，记录原因、暂定决定、可推翻它的结果和下一项可行检查。

**为什么：** “我改了规则，第二次成功”混入了额外上下文、环境修复和尝试次数，不能独立归因于规则。

**例：** 比较“立即修复”和“先复现再修复”的指导，对同一导出 bug 用隔离副本和冻结测试。负对照是只改 UI 提示却保留重复请求；合法变体是禁用按钮或请求去重，两者均可满足合同。记录每个候选的真实改动和验收结果。

**容易踩坑：** 连续修补同一目录算独立试验；看到失败后修改 grader；只留最佳一次。以上是**方法示例，未在此文执行**。模板：[比较协议](../templates/comparison-protocol.md)。

## 5. 有边界地委派，父 agent 收口

**何时用：** 可以独立探索、研究、实现或评审，且并行能改善速度或信心时。依赖上游结果的工作顺序做。

**动作：** 先发现实际可用角色。每个任务给目标、原始证据、范围、约束、完成条件；实现 worker 拥有明确文件/模块，说明共享工作区、不得覆盖他人修改。研究和 review 只读。主 agent 保留用户选定的模型与 effort；常规子任务按当前可用能力/成本选择，不能固定某个型号或声称未测量的省钱。父 agent 检查返回证据、解决冲突、集成并最终验证。

**为什么：** 并行节省的是独立工作的等待时间，不会自动解决边界冲突或错误结论。

**例：** 一个 worker 仅负责 CSV 序列化，另一个只读研究浏览器编码兼容，父 agent 接入下载流程。二者无需同时编辑下载组件。

**容易踩坑：** 给出“全面检查”却没有范围；子 agent 完成消息直接当验收；为了做终端命令额外打开桌面代理。模板：[worker 任务单](../templates/worker-task.md)。

## 6. 独立评审：给事实，不给预期判决

**何时用：** 实质代码改动、重要计划、权限/数据边界；普通小改用相称的检查。

**动作：** 支持时用没有父会话历史的新 reviewer。提供用户目标、约束、当前 source/diff、原始验证和 rubric；不提供希望发现的 bug、上轮结论或偏好候选。返回的问题由父 agent 回到源码或复现验证，修复真实问题，说明有证据的不同意见并重跑受影响检查。相同 reviewer 的复查标为复查。

**为什么：** 减少“沿着作者结论找证据”，同时保留判断所需产品要求。

**例：** 审核“导出应排除未授权记录”的实现，给权限合同和 diff；不说“我认为这里一定存在越权”。即使 reviewer 报告问题，也须用实际数据边界复核。

**容易踩坑：** 只换角色名但仍共享全部历史；未收到评审就标为 reviewed；为保持盲审隐藏必要需求。不可用时写“独立评审 NOT RUN，自查和实际检查如下”，不能默默取消项目硬门槛。模板：[review 任务单](../templates/review-brief.md)。

## 7. 开发与调试：先证明哪里错，再修哪里

**何时用：** 新生产行为、bug、实质重构；环境/配置问题用原操作和原生验证。

**动作：** 记录预期/实际、最小输入、版本、真实退出码；先区分应用、工具链、权限、网络和服务故障。对假设写预测与反证，用最小实验区分原因。bug/new behavior 先跑有意义的红色测试，确认失败来自目标行为；修复后跑 green，再必要重构。已覆盖纯重构保持现有 green，不制造假失败。使用项目的 type/lint/build/test；覆盖率只报真实范围，80% 是有工具支持时的新行为目标，不是正确性证明。

**为什么：** 多个猜测一起改，即使成功也无法知道原因；测试只照抄实现公式则无法约束正确性。

**例：** 时间筛选丢失结束当天记录，先用边界时间 fixture 复现，再决定时区转换在哪层修正；不要同时重写数据库和界面日期组件。

**容易踩坑：** 重跑直到偶然通过；跳过测试求 green；把构建依赖缺失解释为业务错误。模板：[故障调查](../templates/debug-record.md)。

## 8. 验证发生在所声称的边界

**何时用：** 完成前、重要变更后、修复评审发现的问题后。

**动作：** 用项目要求的检查，保留原命令退出码，区分 baseline failure、新失败、跳过、超时。交互变化在可用真实浏览器中执行相关流程；若声称后端/持久化成功，要验证真实服务或存储边界。视觉文档渲染后检查实际内容、尺寸、溢出；配置用解析器和运行时能力检查；文案不编造应用测试覆盖率。最后看 staged/unstaged/untracked 和必要的基线 diff，保留无关修改。

**为什么：** 每种证据只支持一部分结论。

| 证据 | 能支持 | 不能单独支持 |
| --- | --- | --- |
| 单元测试 / mock | 受控条件下的局部逻辑 | 真实外部系统可用 |
| build / type / lint | 构建与静态约束 | 用户流程、可读性、偏好 |
| 真实浏览器操作 | 已执行条件下的界面流程 | 未覆盖设备、WAN、真实人的价值判断 |
| 渲染图检查 | 被查看版本的版式/视觉问题 | 读者理解和实际传播效果 |
| Agent rubric review | 模型按 rubric 的评价 | 人类试验、一般质量提升 |
| 真实参与者比较 | 已招募人群和条件下的观察 | 任意人群或任务的普遍效果 |

**例：** 下载流程：点击 → 等待请求结束 → 检查下载文件字节/内容 → 重新打开页面检查状态恢复。单独显示成功 toast 不能证明文件有效。

**容易踩坑：** `command | tail` 后把 tail 的退出码当 command 成功；截图存在但没有打开；解析 TOML 成功就称所有 MCP 在当前会话可用。

## 9. 交接、上下文压缩与运行位置

**何时用：** 长任务阶段转换、上下文膨胀、跨本地/WSL/远程工作。

**动作：** 在现有任务笔记保留目标、最新约束、决定/理由、文件归属、检查结果、失败历史、运行中的进程、阻塞和一个下一步。只用客户端实际支持的压缩机制；恢复后重核未完成状态，不重启整个任务。代码在哪个环境就用该环境的工具链；Windows 能访问 WSL 文件不等于应使用 Windows Node。远程任务需要真实可用环境、明确授权、最小文件 allowlist、精确 base/patch、资源/网络/输出合同；返回结果仍须核对并本地验证。

**为什么：** 笔记保存的是下一步的依据，不能把所有日志或私人状态搬过去。

**例：** 研究结束进入实现：保存选型理由、版本和验收；无需复制整个网页。Linux 项目通过指定发行版和目录运行测试，记录这只是 Windows→WSL bridge 验证。

**容易踩坑：** 把压缩当重置授权或遗忘失败；将云工具已安装当可用执行环境；上传整个家目录。模板：[交接](../templates/handoff.md)。

## 10. 从证据转成可公开内容

**何时用：** 把实际工作改写成文章、教程、社交内容或演示。

**动作：** 先选允许公开的材料，再提取一项真实主张；说明读者问题、实际条件、局限和可执行动作。按平台调整结构与长度，保留作者真正的语气；没有来源的经历、错误、数字不补写。保留实际阅读版本和出处；截图、代码、日志只使用筛选后的公开片段。草拟、上传、发布是不同动作，后两者按当次授权。

**为什么：** 格式适配可以改变呈现，不能把提案写成实测，把工具数量写成能力提升。

**例：** “我把重复导出检查写进 Skill”需要实际规则/产物证据；若只是演示，写明“中性重演”。同一材料可改成团队操作说明，不必限定社交平台。

**容易踩坑：** 为像真人而捏造第一人称经历；把 AI reviewer 的偏好写成用户反馈；正文写完就默认发布。模板：[公开主张记录](../templates/public-claim.md)。

## 一条完整的跨项目示例（说明性，未作为实测）

任务是“修复报表导出日期范围错误”。先读项目规则/状态/CI，确定包含结束日的验收；查当前日期库文档，列出时区边界假设；写失败回归并确认 red；有需要时委派一个只读 worker 检查 UI 的日期传递，主 agent 修改服务层；使用独立 reviewer 审查合同、source/diff 和原始检查；复核发现后修订，运行相关检查与真实浏览器下载；检查文件内容与数据来源；交付代码与验证缺口，保存下一步。是否发布、推送、部署仍取决于已有授权。没有真实数据服务时，只能报告受控测试和浏览器前端部分，不能宣布生产导出已修复。
